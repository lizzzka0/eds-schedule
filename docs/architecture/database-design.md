# Проектирование базы данных EDS Schedule

**Проект:** Сервис электронного расписания Екатеринбургской духовной семинарии

**Дата начала проектирования:** 26.11.2026

**Версия модели:** 0.1

**Статус:** предварительное проектирование.

## 1. Назначение базы данных

База данных предназначена для централизованного хранения сведений об учебном процессе, учебных ресурсах, расписании занятий и учётных записях администраторов.

Проектирование осуществляется на основании объектной модели, представленной в файле `domain-model.md`.

## 2. Требования к базе данных

- Постоянное хранение информации.
- Обеспечение целостности и согласованности данных.
- Минимизация дублирования информации.
- Хранение черновиков, опубликованных и архивных версий расписания.
- Сохранение исторических данных.
- Поддержка фильтрации расписания.
- Безопасное хранение учётных данных.
- Возможность дальнейшего расширения структуры.

## 3. Используемые технологии

| Параметр | Значение |
|---|---|
| СУБД | PostgreSQL |
| Средство администрирования | DBeaver 26.2.2 |
| Сервер | localhost |
| Порт | 5432 |
| База данных | eds_schedule |
| Схема | schedule |
| search_path | schedule |
| ORM | Prisma (планируется) |

При проектировании предусматривается использование первичных и внешних ключей, ограничений NOT NULL, UNIQUE и CHECK.

Структура базы данных будет проверяться на соответствие требованиям третьей нормальной формы (3НФ).

## 4. Организация пространства хранения данных

26.11.2026 создана отдельная база данных `eds_schedule` на существующем локальном сервере PostgreSQL.

Для хранения объектов приложения создана пользовательская схема `schedule`.

Настроен путь поиска `search_path`, содержащий только схему `schedule`.

Стандартная схема `public` сохраняется, но не используется для хранения прикладных таблиц.

SQL-команды инициализации базы данных документируются в файле `database/01_init_database.sql`.

Создание таблиц и дальнейшее изменение их структуры планируется выполнять посредством миграций Prisma.

На текущем этапе база данных и схема созданы. Проектирование таблиц находится на начальной стадии.
## 5. Проектирование таблиц учебных периодов

### 5.1. Таблица academic_years

Предназначена для хранения сведений об учебных годах.

| Столбец | Тип данных | Ограничения | Назначение |
|---|---|---|---|
| id | INTEGER | PK, автогенерация | Идентификатор учебного года |
| name | VARCHAR(9) | NOT NULL, UNIQUE | Наименование учебного года |
| start_date | DATE | NOT NULL | Дата начала |
| end_date | DATE | NOT NULL | Дата окончания |

Дополнительные ограничения:

- CHECK (start_date <= end_date).
- Наименование учебного года представляется в формате YYYY/YYYY.

### 5.2. Таблица semesters

Предназначена для хранения сведений о семестрах.

| Столбец | Тип данных | Ограничения | Назначение |
|---|---|---|---|
| id | INTEGER | PK, автогенерация | Идентификатор семестра |
| academic_year_id | INTEGER | FK, NOT NULL | Идентификатор учебного года |
| number | INTEGER | NOT NULL | Порядковый номер семестра |
| start_date | DATE | NOT NULL | Дата начала |
| end_date | DATE | NOT NULL | Дата окончания |

Дополнительные ограничения:

- UNIQUE (academic_year_id, number).
- CHECK (number > 0).
- CHECK (start_date <= end_date).
- FOREIGN KEY (academic_year_id) REFERENCES academic_years(id) ON DELETE RESTRICT.

Принадлежность диапазона дат семестра соответствующему учебному году проверяется серверной логикой.

### 5.3. Таблица academic_weeks

Предназначена для хранения сведений об учебных неделях.

| Столбец | Тип данных | Ограничения | Назначение |
|---|---|---|---|
| id | INTEGER | PK, автогенерация | Идентификатор недели |
| semester_id | INTEGER | FK, NOT NULL | Идентификатор семестра |
| number | INTEGER | NOT NULL | Порядковый номер недели |
| start_date | DATE | NOT NULL | Дата начала |
| end_date | DATE | NOT NULL | Дата окончания |

Дополнительные ограничения:

- UNIQUE (semester_id, number).
- CHECK (number > 0).
- CHECK (start_date <= end_date).
- FOREIGN KEY (semester_id) REFERENCES semesters(id) ON DELETE RESTRICT.

Принадлежность диапазона дат учебной недели соответствующему семестру проверяется серверной логикой.

### 5.4. Связи между таблицами

- academic_years — semesters: один ко многим.
- semesters — academic_weeks: один ко многим.

Каждый семестр относится к одному учебному году, каждая учебная неделя — к одному семестру.

### 5.5. Предварительный анализ нормализации

Атрибуты таблиц содержат атомарные значения. Первичные ключи являются простыми, неключевые атрибуты характеризуют соответствующие сущности.

Сведения об учебном годе не дублируются в таблице semesters, а сведения о семестре не дублируются в таблице academic_weeks.

На предварительном уровне структура соответствует требованиям третьей нормальной формы при принятых функциональных зависимостях.

Окончательная проверка нормализации будет проведена после проектирования всех таблиц базы данных.
## 6. Проектирование таблиц организации обучения

### 6.1. Таблица educational_programs

Предназначена для хранения сведений об образовательных программах.

| Столбец | Тип данных | Ограничения | Назначение |
|---|---|---|---|
| id | INTEGER | PK, автогенерация | Идентификатор программы |
| name | VARCHAR(255) | NOT NULL, UNIQUE | Наименование программы |

Дополнительные ограничения:

- Наименование образовательной программы не должно быть пустым.

### 6.2. Таблица study_groups

Предназначена для хранения сведений об учебных группах.

| Столбец | Тип данных | Ограничения | Назначение |
|---|---|---|---|
| id | INTEGER | PK, автогенерация | Идентификатор группы |
| program_id | INTEGER | FK, NOT NULL | Идентификатор образовательной программы |
| name | VARCHAR(100) | NOT NULL | Наименование группы |
| study_form | ENUM | NOT NULL | Форма обучения |
| is_active | BOOLEAN | NOT NULL, DEFAULT TRUE | Признак активности группы |

Допустимые значения study_form:

- FULL_TIME — очная форма обучения.
- PART_TIME — заочная форма обучения.

Дополнительные ограничения:

- FOREIGN KEY (program_id) REFERENCES educational_programs(id) ON DELETE RESTRICT.
- Наименование учебной группы не должно быть пустым.

Номер курса не хранится непосредственно в таблице study_groups, поскольку изменяется в зависимости от учебного года.

### 6.3. Таблица subgroups

Предназначена для хранения сведений об учебных подгруппах.

| Столбец | Тип данных | Ограничения | Назначение |
|---|---|---|---|
| id | INTEGER | PK, автогенерация | Идентификатор подгруппы |
| study_group_id | INTEGER | FK, NOT NULL | Идентификатор учебной группы |
| name | VARCHAR(100) | NOT NULL | Наименование подгруппы |
| is_active | BOOLEAN | NOT NULL, DEFAULT TRUE | Признак активности подгруппы |

Дополнительные ограничения:

- UNIQUE (study_group_id, name).
- FOREIGN KEY (study_group_id) REFERENCES study_groups(id) ON DELETE RESTRICT.
- Наименование подгруппы не должно быть пустым.

### 6.4. Таблица group_academic_years

Предназначена для хранения сведений о номере курса учебной группы в соответствующем учебном году.

| Столбец | Тип данных | Ограничения | Назначение |
|---|---|---|---|
| id | INTEGER | PK, автогенерация | Идентификатор записи |
| study_group_id | INTEGER | FK, NOT NULL | Идентификатор учебной группы |
| academic_year_id | INTEGER | FK, NOT NULL | Идентификатор учебного года |
| course | INTEGER | NOT NULL | Номер курса |

Дополнительные ограничения:

- UNIQUE (study_group_id, academic_year_id).
- CHECK (course > 0).
- FOREIGN KEY (study_group_id) REFERENCES study_groups(id) ON DELETE RESTRICT.
- FOREIGN KEY (academic_year_id) REFERENCES academic_years(id) ON DELETE RESTRICT.

Выделение данной таблицы позволяет сохранять историю обучения группы. При переводе группы на следующий курс создаётся запись для нового учебного года без изменения предыдущих сведений.

### 6.5. Связи между таблицами

- educational_programs — study_groups: один ко многим.
- study_groups — subgroups: один ко многим.
- study_groups — group_academic_years: один ко многим.
- academic_years — group_academic_years: один ко многим.

Между учебными группами и учебными годами реализуется связь многие ко многим посредством промежуточной таблицы group_academic_years, содержащей дополнительный атрибут course.

### 6.6. Предварительный анализ нормализации

Сведения об образовательной программе вынесены в самостоятельную таблицу.

Номер курса зависит от сочетания учебной группы и учебного года, поэтому хранится в отдельной таблице.

Это позволяет избежать дублирования сведений и предотвратить аномалии обновления исторических данных.

При принятых функциональных зависимостях структура соответствует требованиям третьей нормальной формы.

### 6.7. Уточнение объектной модели

В процессе проектирования реляционной базы данных выявлена необходимость хранения истории перехода учебных групп между курсами.

Предусматривается добавление класса GroupAcademicYear и перенос свойства course из класса StudyGroup в данный класс.

Изменения будут отражены в объектной модели и UML-диаграмме следующей версии.

Правила перевода групп, уникальности их наименований и организации учебных периодов для различных форм обучения требуют дополнительного уточнения с заказчиком.
## 7. Проектирование таблиц учебных ресурсов

### 7.1. Таблица teachers

Предназначена для хранения сведений о преподавателях образовательной организации.

| Столбец | Тип данных | Ограничения | Назначение |
|---|---|---|---|
| id | INTEGER | PK, автогенерация | Идентификатор преподавателя |
| last_name | VARCHAR(100) | NOT NULL | Фамилия |
| first_name | VARCHAR(100) | NOT NULL | Имя |
| middle_name | VARCHAR(100) | NULL | Отчество |
| title | VARCHAR(150) | NULL | Сан, звание или другое обозначение |
| is_active | BOOLEAN | NOT NULL, DEFAULT TRUE | Признак активности преподавателя |

Дополнительные ограничения:

- Имя и фамилия преподавателя не должны быть пустыми.
- Отчество и дополнительное обозначение являются необязательными.
- Совпадение фамилии, имени и отчества у разных преподавателей допускается.

Полное отображаемое имя преподавателя формируется на уровне серверной логики и не хранится отдельным столбцом.

### 7.2. Таблица disciplines

Предназначена для хранения справочника учебных дисциплин.

| Столбец | Тип данных | Ограничения | Назначение |
|---|---|---|---|
| id | INTEGER | PK, автогенерация | Идентификатор дисциплины |
| name | VARCHAR(255) | NOT NULL, UNIQUE | Полное наименование дисциплины |
| short_name | VARCHAR(100) | NULL | Сокращённое наименование |
| is_active | BOOLEAN | NOT NULL, DEFAULT TRUE | Признак активности дисциплины |

Дополнительные ограничения:

- Полное наименование дисциплины не должно быть пустым.
- Сокращённое наименование является необязательным.

На предварительном этапе одинаковые полные наименования дисциплин считаются относящимися к одной записи справочника. При необходимости это ограничение может быть пересмотрено.

### 7.3. Таблица classrooms

Предназначена для хранения сведений о помещениях, используемых для проведения учебных занятий.

| Столбец | Тип данных | Ограничения | Назначение |
|---|---|---|---|
| id | INTEGER | PK, автогенерация | Идентификатор аудитории |
| number | VARCHAR(30) | NOT NULL, UNIQUE | Номер или обозначение аудитории |
| name | VARCHAR(150) | NULL | Наименование помещения |
| capacity | INTEGER | NULL | Вместимость аудитории |
| is_active | BOOLEAN | NOT NULL, DEFAULT TRUE | Признак активности аудитории |

Дополнительные ограничения:

- Обозначение аудитории не должно быть пустым.
- CHECK (capacity > 0).
- Вместимость аудитории является необязательной.

Строковый тип данных для номера аудитории позволяет хранить обозначения, содержащие цифры и буквы.

Ограничение уникальности номера аудитории принято при условии использования единой системы обозначения помещений. При наличии нескольких учебных корпусов структура может быть дополнена.

### 7.4. Связи между таблицами

- teachers — lessons: один ко многим.
- disciplines — lessons: один ко многим.
- classrooms — lessons: один ко многим, при этом назначение аудитории занятию является необязательным.

Внешние ключи размещаются в таблице lessons.

Для обеспечения ссылочной целостности предусматривается использование ON DELETE RESTRICT.

### 7.5. Управление активностью учебных ресурсов

Для преподавателей, дисциплин и аудиторий предусмотрен логический атрибут is_active.

Деактивация записи позволяет исключить ресурс из списка доступных для назначения новых занятий без физического удаления связанных данных.

Ранее созданные учебные занятия сохраняют ссылки на соответствующие записи справочников.

Проверка активности ресурсов при назначении на новые занятия выполняется серверной логикой.

Для сохранения исторических наименований при изменении записей справочников потребуется дополнительное архитектурное решение.

### 7.6. Предварительный анализ нормализации

Каждая таблица представляет самостоятельную сущность предметной области.

Сведения о преподавателях, дисциплинах и аудиториях хранятся централизованно и не дублируются в таблице учебных занятий.

Неключевые атрибуты характеризуют соответствующую сущность и зависят от её первичного ключа.

Вычисляемое полное имя преподавателя не хранится в базе данных, поскольку может быть сформировано из имеющихся атрибутов.

При принятых функциональных зависимостях структура таблиц соответствует требованиям третьей нормальной формы.

### 7.7. Планируемые проверки целостности

- Проверка уникальности первичных ключей.
- Проверка обязательных полей.
- Проверка уникальности наименований дисциплин.
- Проверка уникальности обозначений аудиторий.
- Проверка отклонения отрицательной и нулевой вместимости аудитории.
- Проверка возможности сохранения необязательных полей со значением NULL.
- Проверка запрета удаления ресурсов, связанных с учебными занятиями.
- Проверка сохранения связанных данных после деактивации ресурса.

Фактические проверки будут выполнены после создания таблиц посредством миграций Prisma.
## 8. Проектирование таблиц расписания и учебных занятий

### 8.1. Таблица schedules

Предназначена для хранения версий расписания учебных занятий на определённую учебную неделю.

| Столбец | Тип данных | Ограничения | Назначение |
|---|---|---|---|
| id | INTEGER | PK, автогенерация | Идентификатор расписания |
| academic_week_id | INTEGER | FK, NOT NULL | Идентификатор учебной недели |
| version | INTEGER | NOT NULL | Номер версии расписания |
| status | ENUM | NOT NULL, DEFAULT DRAFT | Статус расписания |
| created_at | TIMESTAMPTZ | NOT NULL, DEFAULT CURRENT_TIMESTAMP | Дата и время создания |
| published_at | TIMESTAMPTZ | NULL | Дата и время публикации |

Допустимые значения status:

- DRAFT — черновик.
- PUBLISHED — опубликованное расписание.
- ARCHIVED — архивная версия.

Дополнительные ограничения:

- UNIQUE (academic_week_id, version).
- CHECK (version > 0).
- FOREIGN KEY (academic_week_id) REFERENCES academic_weeks(id) ON DELETE RESTRICT.
- Для черновика дата публикации должна отсутствовать.
- Для опубликованных и архивных версий дата публикации должна быть указана.
- Дата публикации не должна предшествовать дате создания расписания.

Для обеспечения уникальности актуальной опубликованной версии в пределах учебной недели предусматривается использование частичного уникального индекса PostgreSQL.

### 8.2. Таблица lessons

Предназначена для хранения сведений об отдельных учебных занятиях, относящихся к определённой версии расписания.

| Столбец | Тип данных | Ограничения | Назначение |
|---|---|---|---|
| id | INTEGER | PK, автогенерация | Идентификатор занятия |
| schedule_id | INTEGER | FK, NOT NULL | Идентификатор версии расписания |
| group_academic_year_id | INTEGER | FK, NOT NULL | Идентификатор группы в учебном году |
| subgroup_id | INTEGER | FK, NULL | Идентификатор подгруппы |
| teacher_id | INTEGER | FK, NOT NULL | Идентификатор преподавателя |
| discipline_id | INTEGER | FK, NOT NULL | Идентификатор дисциплины |
| classroom_id | INTEGER | FK, NULL | Идентификатор аудитории |
| lesson_date | DATE | NOT NULL | Дата проведения занятия |
| start_time | TIME(0) | NOT NULL | Время начала |
| end_time | TIME(0) | NOT NULL | Время окончания |
| lesson_type | ENUM | NOT NULL | Вид учебного занятия |

Допустимые значения lesson_type:

- LECTURE — лекция.
- SEMINAR — семинар.
- PRACTICAL — практическое занятие.
- CONSULTATION — консультация.
- EXAM — экзамен.
- CREDIT — зачёт.

Дополнительные ограничения:

- CHECK (start_time < end_time).
- FOREIGN KEY (schedule_id) REFERENCES schedules(id) ON DELETE RESTRICT.
- FOREIGN KEY (group_academic_year_id) REFERENCES group_academic_years(id) ON DELETE RESTRICT.
- FOREIGN KEY (subgroup_id) REFERENCES subgroups(id) ON DELETE RESTRICT.
- FOREIGN KEY (teacher_id) REFERENCES teachers(id) ON DELETE RESTRICT.
- FOREIGN KEY (discipline_id) REFERENCES disciplines(id) ON DELETE RESTRICT.
- FOREIGN KEY (classroom_id) REFERENCES classrooms(id) ON DELETE RESTRICT.

При отсутствии значения subgroup_id занятие предназначается для всей учебной группы.

Отсутствие значения classroom_id допускается на этапе составления расписания. Возможность публикации таких занятий требует уточнения с заказчиком.

### 8.3. Связи между таблицами

- academic_weeks — schedules: один ко многим.
- schedules — lessons: один ко многим.
- group_academic_years — lessons: один ко многим.
- subgroups — lessons: один ко многим, необязательная связь со стороны занятия.
- teachers — lessons: один ко многим.
- disciplines — lessons: один ко многим.
- classrooms — lessons: один ко многим, необязательная связь со стороны занятия.

Каждое учебное занятие принадлежит только одной версии расписания.

### 8.4. Обеспечение версионности расписания

Для каждой учебной недели предусматривается возможность хранения нескольких версий расписания.

Номер версии должен быть уникальным в пределах соответствующей учебной недели.

Одновременно допускается существование не более одной опубликованной версии расписания для одной учебной недели.

При необходимости изменения опубликованного расписания создаётся новый черновик с независимыми копиями учебных занятий.

Публикация новой версии и архивирование предыдущей выполняются в рамках одной транзакции.

Редактирование опубликованных и архивных версий запрещается серверной логикой приложения.

### 8.5. Проверки на уровне серверной логики

Помимо ограничений базы данных, предусматриваются следующие проверки:

- Дата занятия находится в пределах учебной недели.
- Учебный год группы соответствует учебному году расписания.
- Выбранная подгруппа принадлежит соответствующей учебной группе.
- Назначаемые на новые занятия учебные ресурсы являются активными.
- Дата и время занятия имеют корректный формат.
- Отсутствуют недопустимые конфликты преподавателей, аудиторий, групп и подгрупп.
- Изменение занятия выполняется только в черновике.
- При публикации проверяется полнота обязательных сведений.

Не все перечисленные ограничения могут быть реализованы посредством обычных CHECK и FOREIGN KEY, поскольку некоторые из них требуют анализа нескольких таблиц и записей.

### 8.6. Хранение даты и времени

Для хранения даты учебного занятия используется тип DATE.

Время начала и окончания занятия хранится с использованием типа TIME(0) без часового пояса.

При обработке расписания используется местное время Екатеринбурга (Asia/Yekaterinburg).

Для хранения времени создания и публикации версий расписания применяется тип TIMESTAMPTZ, позволяющий однозначно определять момент выполнения операции.

При экспорте расписания в формат iCalendar необходимо учитывать часовой пояс образовательной организации.

### 8.7. Предварительный анализ нормализации

Таблица lessons содержит ссылки на самостоятельные сущности предметной области.

Наименования дисциплин, преподавателей, аудиторий и учебных групп непосредственно в таблице занятий не дублируются.

Связь с таблицей group_academic_years позволяет получать сведения о курсе группы в соответствующем учебном году.

Номер учебной недели, учебный год и статус расписания не дублируются в таблице lessons, поскольку определяются через связанные записи.

При принятых функциональных зависимостях структура соответствует требованиям третьей нормальной формы.

### 8.8. Планируемые проверки целостности

- Проверка корректности внешних ключей.
- Проверка обязательности полей.
- Проверка уникальности номера версии расписания.
- Проверка невозможности существования двух опубликованных версий одной недели.
- Проверка корректности временного интервала занятия.
- Проверка принадлежности занятия учебной неделе.
- Проверка соответствия учебного года группы учебному году расписания.
- Проверка принадлежности подгруппы учебной группе.
- Проверка запрета удаления связанных записей.
- Проверка атомарности публикации расписания.
- Проверка независимости занятий различных версий расписания.

Фактические проверки будут выполнены после создания структуры базы данных и реализации серверной логики.

### 8.9. Уточнение объектной модели

В процессе проектирования базы данных принято предварительное решение связывать учебное занятие с сущностью GroupAcademicYear вместо непосредственной связи с StudyGroup.

## 9. Проектирование таблицы учётных записей

### 9.1. Таблица users

Предназначена для хранения учётных записей сотрудников, имеющих доступ к административной части сервиса электронного расписания.

| Столбец | Тип данных | Ограничения | Назначение |
|---|---|---|---|
| id | INTEGER | PK, автогенерация | Идентификатор пользователя |
| username | VARCHAR(100) | NOT NULL, UNIQUE | Имя пользователя для входа |
| password_hash | TEXT | NOT NULL | Хеш пароля |
| full_name | VARCHAR(255) | NOT NULL | Полное имя пользователя |
| role | ENUM | NOT NULL, DEFAULT ADMIN | Роль пользователя |
| is_active | BOOLEAN | NOT NULL, DEFAULT TRUE | Признак активности учётной записи |
| created_at | TIMESTAMPTZ | NOT NULL, DEFAULT CURRENT_TIMESTAMP | Дата и время создания записи |

Допустимые значения role:

- ADMIN — администратор расписания.

В дальнейшем перечень ролей может быть расширен при необходимости разграничения полномочий сотрудников.

### 9.2. Ограничения целостности

- Имя пользователя должно быть уникальным.
- Имя пользователя, полное имя и хеш пароля не должны быть пустыми.
- Роль должна соответствовать одному из допустимых значений перечисления.
- Признак активности учётной записи должен иметь логическое значение.

### 9.3. Обеспечение безопасности данных

Пароли пользователей не должны храниться в открытом виде.

Перед сохранением пароля предусматривается его обработка специализированным алгоритмом хеширования паролей.

Хеш пароля используется исключительно серверной частью приложения и не должен передаваться в клиентскую часть посредством REST API.

Проверка учётных данных, активности пользователя и его полномочий осуществляется серверной логикой.

Самостоятельная регистрация администраторов через публичную часть приложения не предусматривается.

### 9.4. Управление активностью учётных записей

Для ограничения доступа сотрудника предусматривается изменение значения атрибута is_active.

Деактивация учётной записи позволяет прекратить доступ пользователя к административной части без необходимости физического удаления записи.

Неактивный пользователь не должен иметь возможности выполнять защищённые операции, в том числе при наличии ранее выданного токена доступа.

### 9.5. Связи с другими таблицами

На текущем этапе таблица users является самостоятельной.

Прямые связи между учётными записями и преподавателями или учебными группами не предусматриваются, поскольку просмотр опубликованного расписания осуществляется без аутентификации.

В дальнейшем структура базы данных может быть дополнена средствами регистрации действий администраторов и хранения сведений об авторах изменений расписания.

### 9.6. Предварительный анализ нормализации

Все атрибуты таблицы содержат атомарные значения.

Первичный ключ является простым. Неключевые атрибуты характеризуют соответствующую учётную запись.

Имя пользователя является альтернативным ключом.

При принятых функциональных зависимостях структура таблицы соответствует требованиям третьей нормальной формы.

### 9.7. Планируемые проверки

- Проверка уникальности имени пользователя.
- Проверка обязательности заполнения полей.
- Проверка допустимости значения роли.
- Проверка значения активности по умолчанию.
- Проверка отсутствия паролей в открытом виде.
- Проверка отсутствия хеша пароля в ответах REST API.
- Проверка ограничения доступа для деактивированных пользователей.

Проверки ограничений базы данных будут выполняться после создания таблицы. Проверки безопасности и управления доступом будут проводиться после реализации соответствующих серверных компонентов.

### 10.2. Анализ нормализации

Первая нормальная форма обеспечивается использованием атомарных значений атрибутов и отсутствием повторяющихся групп данных.

Вторая нормальная форма обеспечивается полной функциональной зависимостью неключевых атрибутов от потенциальных ключей соответствующих таблиц.

Третья нормальная форма обеспечивается выделением самостоятельных сущностей и устранением транзитивных зависимостей неключевых атрибутов.

Сведения об образовательных программах, преподавателях, дисциплинах, аудиториях и учебных периодах хранятся в самостоятельных таблицах.

Для сохранения истории перехода учебных групп между курсами предусмотрена таблица group_academic_years. Номер курса функционально зависит от сочетания идентификатора учебной группы и идентификатора учебного года.

При принятых функциональных зависимостях спроектированная структура соответствует требованиям третьей нормальной формы.

### 10.3. Обеспечение целостности данных

Для обеспечения целостности предусматривается использование следующих механизмов PostgreSQL:

- PRIMARY KEY — идентификация записей.
- FOREIGN KEY — обеспечение ссылочной целостности.
- NOT NULL — обязательность заполнения атрибутов.
- UNIQUE — обеспечение уникальности значений.
- CHECK — проверка допустимых значений.
- DEFAULT — установка значений по умолчанию.
- ON DELETE RESTRICT — предотвращение удаления связанных записей.
- Частичный уникальный индекс — обеспечение уникальности опубликованной версии расписания.
- Транзакции — обеспечение атомарности операций публикации.

Ограничения, требующие анализа нескольких связанных записей, дополнительно проверяются серверной логикой.

### 10.4. Согласованность с объектной моделью

### 10.5. Предварительные допущения и ограничения

Для первоначальной реализации предполагается использование единого учебного календаря образовательной организации.

Не допускается пересечение диапазонов дат семестров одного учебного года и учебных недель одного семестра. Проверяется также принадлежность дочерних учебных периодов родительским.

Подгруппы одной учебной группы считаются непересекающимися по составу обучающихся.

Каждое занятие связано с одной учебной группой или её подгруппой и одним преподавателем.

Окончательного уточнения требуют:

- Совместные занятия нескольких учебных групп.
- Назначение нескольких преподавателей на одно занятие.
- Различия учебных календарей разных форм обучения.
- Сохранение исторических наименований справочников.
- Возможность частичной публикации расписания.
- Возможность публикации занятий без назначенной аудитории.

Перечисленные допущения могут быть пересмотрены при уточнении требований заказчика.
