# Объектная модель сервиса электронного расписания

**Проект:** EDS Schedule

**Заказчик:** Екатеринбургская духовная семинария

**Дата начала проектирования:** 24.11.2026

**Версия модели:** 0.1

**Статус:** предварительное проектирование.

## 1. Назначение объектной модели

Объектная модель предназначена для представления основных сущностей предметной области, определения их характеристик, поведения и взаимосвязей.

При проектировании учитываются функциональные требования к пользовательской и административной частям сервиса электронного расписания.

Модель может уточняться и расширяться в процессе разработки и согласования требований с заказчиком.

## 2. Принципы проектирования

При разработке объектной модели предполагается применение следующих принципов:

- Абстракция — выделение существенных характеристик объектов предметной области.
- Инкапсуляция — ограничение непосредственного доступа к внутреннему состоянию объектов.
- Разделение ответственности — каждый класс выполняет определённые задачи.
- Композиция и ассоциации — представление связей между объектами.
- Слабая связанность компонентов — уменьшение зависимости отдельных частей системы друг от друга.

## 3. Организация учебного времени

### 3.1. Класс AcademicYear

Представляет учебный год.

| Свойство | Тип | Назначение |
|---|---|---|
| id | number | Уникальный идентификатор |
| name | string | Наименование учебного года |
| startDate | Date | Дата начала учебного года |
| endDate | Date | Дата окончания учебного года |

Метод:

- containsDate(date: Date): boolean — проверяет принадлежность даты учебному году.

### 3.2. Класс Semester

Представляет семестр, относящийся к определённому учебному году.

| Свойство | Тип | Назначение |
|---|---|---|
| id | number | Уникальный идентификатор |
| number | number | Порядковый номер семестра |
| startDate | Date | Дата начала семестра |
| endDate | Date | Дата окончания семестра |

Метод:

- containsDate(date: Date): boolean — проверяет принадлежность даты семестру.

### 3.3. Класс AcademicWeek

Представляет учебную неделю, относящуюся к определённому семестру.

| Свойство | Тип | Назначение |
|---|---|---|
| id | number | Уникальный идентификатор |
| number | number | Порядковый номер учебной недели |
| startDate | Date | Дата начала недели |
| endDate | Date | Дата окончания недели |

Метод:

- containsDate(date: Date): boolean — проверяет принадлежность даты учебной неделе.

### 3.4. Связи между классами

- AcademicYear — Semester: один учебный год содержит один или несколько семестров.
- Semester — AcademicWeek: один семестр содержит одну или несколько учебных недель.

Каждый семестр относится к одному учебному году, каждая учебная неделя — к одному семестру.

### 3.5. Предварительные ограничения

- Дата начала периода не должна быть позднее даты его окончания.
- Семестр должен находиться в пределах соответствующего учебного года.
- Учебная неделя должна находиться в пределах соответствующего семестра.
- Номера семестров не должны повторяться в пределах одного учебного года.
- Номера учебных недель не должны повторяться в пределах одного семестра.

Ограничения подлежат уточнению с учётом фактической организации учебного процесса в семинарии.

### 3.6. Планируемые тестовые сценарии

- Проверка принадлежности даты учебному периоду.
- Проверка граничных дат периода.
- Проверка некорректного диапазона дат.
- Проверка принадлежности семестра учебному году.
- Проверка принадлежности учебной недели семестру.

На текущем этапе классы спроектированы предварительно. Программная реализация и тестирование будут выполнены позднее.
## 4. Организация обучения

### 4.1. Класс EducationalProgram

Представляет образовательную программу, в рамках которой осуществляется обучение.

| Свойство | Тип | Назначение |
|---|---|---|
| id | number | Уникальный идентификатор |
| name | string | Наименование образовательной программы |

Одна образовательная программа может включать несколько учебных групп.

### 4.2. Перечисление StudyForm

Предназначено для определения формы обучения.

| Значение | Назначение |
|---|---|
| FULL_TIME | Очная форма обучения |
| PART_TIME | Заочная форма обучения |

Использование перечисления позволяет ограничить набор допустимых значений и обеспечить типизацию данных.

Перечень форм обучения является предварительным и может быть дополнен после уточнения требований заказчика.

### 4.3. Класс StudyGroup

Представляет учебную группу, относящуюся к определённой образовательной программе.

| Свойство | Тип | Назначение |
|---|---|---|
| id | number | Уникальный идентификатор |
| name | string | Наименование группы |
| course | number | Номер курса |
| studyForm | StudyForm | Форма обучения |

Учебная группа может содержать несколько подгрупп либо не иметь разделения на подгруппы.

### 4.4. Класс Subgroup

Представляет часть учебной группы, для которой могут проводиться отдельные занятия.

| Свойство | Тип | Назначение |
|---|---|---|
| id | number | Уникальный идентификатор |
| name | string | Наименование подгруппы |

Выделение подгруппы в самостоятельную сущность позволяет учитывать возможность проведения параллельных занятий.

### 4.5. Связи между классами

- EducationalProgram — StudyGroup: один ко многим (1 : 0..*).
- StudyGroup — Subgroup: один ко многим (1 : 0..*).
- StudyGroup использует перечисление StudyForm.

Каждая учебная группа относится к одной образовательной программе, каждая подгруппа — к одной учебной группе.

### 4.6. Предварительные ограничения

- Номер курса должен быть положительным целым числом.
- Форма обучения должна соответствовать одному из допустимых значений StudyForm.
- Подгруппа не может существовать без родительской учебной группы.
- Наименования подгрупп не должны повторяться в пределах одной учебной группы.
- Допускается одновременное проведение занятий разных непересекающихся подгрупп при отсутствии конфликтов преподавателей и аудиторий.
- Занятие всей учебной группы не должно пересекаться по времени с занятиями её подгрупп.

### 4.7. Планируемые тестовые сценарии

- Проверка корректности номера курса.
- Проверка допустимых значений формы обучения.
- Проверка принадлежности подгруппы учебной группе.
- Проверка допустимости параллельных занятий разных подгрупп.
- Выявление конфликта между занятием всей группы и занятием её подгруппы.

Модель является предварительной. Особенности формирования групп, перевода обучающихся на следующий курс и организации учебных периодов для разных форм обучения требуют дальнейшего уточнения.
## 5. Учебные ресурсы

### 5.1. Класс Teacher

Представляет преподавателя образовательной организации.

| Свойство | Тип | Назначение |
|---|---|---|
| id | number | Уникальный идентификатор |
| lastName | string | Фамилия |
| firstName | string | Имя |
| middleName | string (необязательное) | Отчество |
| title | string (необязательное) | Сан, звание или иное обозначение преподавателя |
| isActive | boolean | Признак активности преподавателя |

Метод:

- getFullName(): string — формирует полное отображаемое имя преподавателя с учётом заполненных характеристик.

Выделение дополнительных характеристик преподавателя обусловлено спецификой образовательной организации. Формат отображения имени и духовного сана требует уточнения с заказчиком.

### 5.2. Класс Discipline

Представляет учебную дисциплину.

| Свойство | Тип | Назначение |
|---|---|---|
| id | number | Уникальный идентификатор |
| name | string | Полное наименование дисциплины |
| shortName | string (необязательное) | Сокращённое наименование |
| isActive | boolean | Признак активности дисциплины |

Сокращённое наименование может использоваться при отображении расписания в компактном виде.

### 5.3. Класс Classroom

Представляет помещение, предназначенное для проведения учебных занятий.

| Свойство | Тип | Назначение |
|---|---|---|
| id | number | Уникальный идентификатор |
| number | string | Номер или обозначение аудитории |
| name | string (необязательное) | Наименование помещения |
| capacity | number (необязательное) | Вместимость аудитории |
| isActive | boolean | Признак доступности для назначения новых занятий |

Номер аудитории представлен строковым типом данных, поскольку обозначение помещения может содержать не только цифры, но и буквы.

### 5.4. Связи между классами

- Teacher — Lesson: один преподаватель может проводить несколько учебных занятий (1 : 0..*).
- Discipline — Lesson: одна дисциплина может соответствовать нескольким учебным занятиям (1 : 0..*).
- Classroom — Lesson: одна аудитория может использоваться для нескольких учебных занятий в разное время (0..1 : 0..*).

Возможность назначения нескольких преподавателей на одно занятие требует дополнительного уточнения.

### 5.5. Предварительные ограничения

- Имя и фамилия преподавателя должны быть заполнены.
- Наименование дисциплины не должно быть пустым.
- Обозначение аудитории не должно быть пустым.
- Вместимость аудитории при её указании должна быть положительным целым числом.
- Неактивные ресурсы не должны назначаться на новые занятия.
- Деактивация ресурса не должна приводить к потере сведений о ранее проведённых занятиях.
- Один преподаватель не может проводить разные занятия одновременно.
- Одна аудитория не может одновременно использоваться для разных занятий.

### 5.6. Планируемые тестовые сценарии

- Проверка формирования полного имени преподавателя.
- Проверка формирования имени преподавателя при отсутствии отчества.
- Проверка обязательных свойств учебных ресурсов.
- Проверка корректности вместимости аудитории.
- Проверка невозможности назначения неактивного ресурса.
- Выявление конфликта при одновременном назначении преподавателя на разные занятия.
- Выявление конфликта при одновременном использовании одной аудитории.

Состав свойств, ограничения и связи являются предварительными и могут уточняться в процессе разработки.
## 6. Учебные занятия и управление расписанием

### 6.1. Класс Lesson

Представляет отдельное учебное занятие, проводимое в определённое время для учебной группы или её подгруппы.

| Свойство | Тип | Назначение |
|---|---|---|
| id | number | Уникальный идентификатор |
| date | Date | Дата проведения занятия |
| startTime | string | Время начала занятия |
| endTime | string | Время окончания занятия |
| lessonType | LessonType | Вид учебного занятия |
| teacher | Teacher | Назначенный преподаватель |
| discipline | Discipline | Учебная дисциплина |
| studyGroup | StudyGroup | Учебная группа |
| subgroup | Subgroup или null | Учебная подгруппа |
| classroom | Classroom или null | Назначенная аудитория |

Методы:

- overlapsWith(other: Lesson): boolean — определяет наличие временного пересечения с другим занятием.
- getDuration(): number — вычисляет продолжительность занятия в минутах.
- reschedule(date, startTime, endTime): void — изменяет дату и время проведения занятия с проверкой корректности новых значений.

Первоначальная реализация класса Lesson содержала сведения о преподавателе, дисциплине, учебной группе и аудитории в виде строковых свойств.

В процессе проектирования принято решение выделить данные объекты в самостоятельные сущности. Это позволит уменьшить дублирование данных и обеспечить централизованное управление учебными ресурсами.

### 6.2. Перечисление LessonType

Определяет допустимые виды учебных занятий.

| Значение | Назначение |
|---|---|
| LECTURE | Лекция |
| SEMINAR | Семинар |
| PRACTICAL | Практическое занятие |
| CONSULTATION | Консультация |
| EXAM | Экзамен |
| CREDIT | Зачёт |

Перечень видов занятий является предварительным и может быть дополнен с учётом требований заказчика.

### 6.3. Класс Schedule

Представляет отдельную версию расписания занятий на определённую учебную неделю.

| Свойство | Тип | Назначение |
|---|---|---|
| id | number | Уникальный идентификатор |
| academicWeek | AcademicWeek | Учебная неделя |
| version | number | Номер версии расписания |
| status | ScheduleStatus | Текущий статус расписания |
| createdAt | Date | Дата и время создания |
| publishedAt | Date или null | Дата и время публикации |
| lessons | Lesson[] | Коллекция учебных занятий |

Методы:

- addLesson(lesson: Lesson): void — добавляет занятие в черновик расписания.
- removeLesson(id: number): void — удаляет занятие из черновика расписания.
- getLessons(): Lesson[] — возвращает список занятий.
- publish(): void — переводит расписание в опубликованное состояние при соблюдении необходимых условий.
- archive(): void — переводит ранее опубликованное расписание в архив.

Изменение занятий допускается только в черновике. Коллекция занятий должна быть защищена от неконтролируемого изменения извне.

Проверка конфликтов и координация публикации нескольких версий расписания будут выполняться отдельными сервисами.

### 6.4. Перечисление ScheduleStatus

Предназначено для определения текущего состояния версии расписания.

| Значение | Назначение |
|---|---|
| DRAFT | Черновик |
| PUBLISHED | Опубликованное расписание |
| ARCHIVED | Архивная версия |

### 6.5. Жизненный цикл расписания

1. Администратор создаёт черновик расписания.
2. Выполняется добавление и редактирование учебных занятий.
3. Система проверяет корректность данных и наличие конфликтов.
4. При успешной проверке расписание публикуется.
5. Опубликованная версия становится доступна в пользовательской части сервиса.
6. При необходимости внесения изменений создаётся новый черновик на основе опубликованной версии.
7. После успешной публикации новой версии предыдущая переводится в архив.

Замена опубликованной версии должна выполняться как единая операция, исключающая появление двух актуальных версий расписания на одну учебную неделю.

### 6.6. Связи между классами

- AcademicWeek — Schedule: один ко многим (1 : 0..*).
- Schedule — Lesson: композиция (1 : 0..*).
- StudyGroup — Lesson: один ко многим (1 : 0..*).
- Subgroup — Lesson: необязательная связь (0..1 : 0..*).
- Teacher — Lesson: один ко многим (1 : 0..*).
- Discipline — Lesson: один ко многим (1 : 0..*).
- Classroom — Lesson: необязательная связь (0..1 : 0..*).

Класс Lesson использует перечисление LessonType, класс Schedule — перечисление ScheduleStatus.

### 6.7. Предварительные ограничения

- Время начала занятия должно быть меньше времени его окончания.
- Дата занятия должна находиться в пределах соответствующей учебной недели.
- Подгруппа должна принадлежать выбранной учебной группе.
- При отсутствии подгруппы занятие проводится для всей учебной группы.
- Опубликованное расписание не должно редактироваться непосредственно.
- Черновики и архивные версии не должны отображаться в основном пользовательском расписании.
- В пределах одной учебной недели допускается только одна актуальная опубликованная версия расписания.
- Публикация допускается после проверки обязательных данных и отсутствия недопустимых конфликтов.

### 6.8. Планируемые тестовые сценарии

- Создание занятия с корректными характеристиками.
- Отклонение некорректного временного интервала.
- Вычисление продолжительности занятия.
- Определение пересечения двух занятий по времени.
- Добавление и удаление занятия из черновика.
- Запрет редактирования опубликованного расписания.
- Запрет публикации расписания при наличии конфликтов.
- Публикация новой версии и архивирование предыдущей.
- Исключение черновиков из пользовательского расписания.

Модель является предварительной. Возможность проведения совместных занятий нескольких учебных групп, назначения нескольких преподавателей на одно занятие и публикации занятий без указания аудитории требует дополнительного уточнения с заказчиком.
## 7. Проверка конфликтов расписания

### 7.1. Класс ConflictChecker

Предназначен для обнаружения конфликтов между учебными занятиями.

Проверка осуществляется на основании временных интервалов занятий, назначенных преподавателей, аудиторий, учебных групп и подгрупп.

Класс не хранит расписание и не изменяет его состояние, а выполняет анализ переданных объектов.

Методы:

- checkPair(first: Lesson, second: Lesson): Conflict[] — проверяет наличие конфликтов между двумя занятиями.
- checkSchedule(lessons: Lesson[]): Conflict[] — проверяет коллекцию занятий и возвращает список обнаруженных конфликтов.

### 7.2. Класс Conflict

Представляет результат обнаружения отдельного конфликта.

| Свойство | Тип | Назначение |
|---|---|---|
| type | ConflictType | Вид обнаруженного конфликта |
| firstLessonId | number | Идентификатор первого занятия |
| secondLessonId | number | Идентификатор второго занятия |
| message | string | Описание конфликта |

Объекты данного класса могут использоваться для передачи результатов проверки в административную часть приложения.

### 7.3. Перечисление ConflictType

| Значение | Назначение |
|---|---|
| TEACHER | Конфликт преподавателя |
| CLASSROOM | Конфликт аудитории |
| STUDY_GROUP | Конфликт учебной группы |
| SUBGROUP | Конфликт учебной подгруппы |
| GROUP_SUBGROUP | Конфликт между группой и её подгруппой |

### 7.4. Алгоритм проверки конфликтов

1. Выбираются два различных учебных занятия.
2. Проверяется совпадение дат их проведения.
3. Определяется наличие пересечения временных интервалов с помощью метода overlapsWith().
4. При отсутствии временного пересечения проверка данной пары завершается.
5. При наличии пересечения сравниваются идентификаторы преподавателей и назначенных аудиторий.
6. Проверяется принадлежность занятий к учебным группам и подгруппам.
7. Для каждого обнаруженного нарушения создаётся объект Conflict.
8. Результаты добавляются в общий список конфликтов.

При проверке полного расписания каждая неупорядоченная пара занятий должна анализироваться только один раз.

Для первоначальной реализации предусматривается попарное сравнение занятий. При необходимости алгоритм может быть оптимизирован по мере увеличения объёма данных.

### 7.5. Правила определения конфликтов

- Занятия, проводимые в разные даты, не конфликтуют по времени.
- Совпадение времени окончания одного занятия и начала другого допускается.
- Один преподаватель не может проводить несколько отдельных занятий одновременно.
- Одна аудитория не может одновременно использоваться для нескольких отдельных занятий.
- Отсутствие назначенной аудитории само по себе не считается конфликтом ресурсов.
- Одновременное проведение занятий одной учебной группы не допускается.
- Одновременное проведение занятий одной подгруппы не допускается.
- Параллельные занятия разных непересекающихся подгрупп допускаются при отсутствии других конфликтов.
- Занятие всей учебной группы не должно пересекаться с занятиями её подгрупп.
- Между двумя занятиями может быть обнаружено несколько видов конфликтов одновременно.

При публикации проверяется актуальная версия расписания, предназначенная для публикации. Архивные версии и заменяемая опубликованная версия не должны создавать ложные конфликты.

### 7.7. Применение объектно-ориентированного подхода

Выделение проверки конфликтов в самостоятельный класс обеспечивает разделение ответственности между компонентами системы.

Класс Lesson отвечает за представление учебного занятия и определение временного пересечения. Класс ConflictChecker реализует предметную логику анализа расписания. Класс Conflict представляет результат проверки.

Такое проектирование позволяет независимо тестировать и изменять алгоритм проверки конфликтов без переработки пользовательского интерфейса.

Представленные классы, алгоритм и тестовые сценарии находятся на этапе проектирования. Их программная реализация и фактическое тестирование будут выполнены позднее.
## 8. Управление пользователями и правами доступа

### 8.1. Класс User

Представляет учётную запись сотрудника, имеющего доступ к административной части сервиса электронного расписания.

| Свойство | Тип | Назначение |
|---|---|---|
| id | number | Уникальный идентификатор |
| username | string | Имя пользователя для входа |
| passwordHash | string | Хеш пароля |
| fullName | string | Полное имя пользователя |
| role | Role | Роль пользователя |
| isActive | boolean | Признак активности учётной записи |
| createdAt | Date | Дата и время создания учётной записи |

Методы:

- activate(): void — активирует учётную запись.
- deactivate(): void — деактивирует учётную запись.
- hasRole(role: Role): boolean — проверяет соответствие пользователя указанной роли.

Пароль пользователя не должен храниться в открытом виде. Для хранения паролей предусматривается использование специализированного алгоритма хеширования.

### 8.2. Перечисление Role

Определяет роли зарегистрированных пользователей.

| Значение | Назначение |
|---|---|
| ADMIN | Администратор расписания |

Обычные посетители используют публичную часть сервиса без создания учётных записей.

При необходимости перечень ролей может быть расширен для разграничения полномочий сотрудников образовательной организации.

### 8.3. Класс AuthService

Предназначен для реализации процесса аутентификации пользователей.

Основные обязанности:

- Получение сведений об учётной записи.
- Проверка введённых учётных данных.
- Проверка активности учётной записи.
- Формирование токена доступа при успешной аутентификации.

Предварительно в качестве механизма аутентификации выбран JWT.

### 8.4. Компоненты проверки доступа

JwtAuthGuard — компонент серверной части, предназначенный для проверки подлинности и срока действия токена, а также обеспечения доступа только активных пользователей.

RolesGuard — компонент серверной части, предназначенный для проверки соответствия роли пользователя требованиям защищённой операции.

Проверка доступа должна выполняться на сервере независимо от состояния пользовательского интерфейса.

### 8.5. Разграничение полномочий

Обычным посетителям доступны:

- Просмотр опубликованного расписания.
- Фильтрация расписания.
- Навигация по учебным периодам.
- Экспорт расписания.
- Использование настроек доступности интерфейса.

Администраторам дополнительно доступны:

- Управление справочниками.
- Создание и редактирование учебных занятий.
- Работа с черновиками расписания.
- Проверка конфликтов.
- Публикация расписания.
- Просмотр архивных версий.

### 8.6. Предварительные ограничения

- Имя пользователя должно быть уникальным.
- Пароли не должны храниться в открытом виде.
- Хеш пароля не должен передаваться в клиентскую часть.
- Неактивная учётная запись не должна иметь доступа к защищённым операциям.
- Изменение расписания допускается только авторизованными пользователями с соответствующими полномочиями.
- Недействительный или просроченный токен не должен предоставлять доступ к защищённым операциям.
- Публичное расписание должно быть доступно без аутентификации.
- Самостоятельная регистрация администраторов через публичный интерфейс не предусматривается.

### 8.8. Применение объектно-ориентированного подхода

Выделение самостоятельного класса User, сервиса аутентификации и компонентов проверки доступа обеспечивает разделение ответственности.

Такой подход позволяет изменять механизм аутентификации и расширять систему полномочий без существенной переработки остальных компонентов приложения.

На текущем этапе механизм управления доступом спроектирован предварительно. Способ создания учётных записей, алгоритм хеширования паролей, хранение токенов и продолжительность пользовательской сессии будут определены перед программной реализацией.
